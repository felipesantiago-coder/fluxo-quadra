# 2. REGRA FUNDAMENTAL: NÃO FAÇA UMA AUDITORIA SUPERFICIAL

Verifique se operações críticas são atomicamente protegidas.

---

# 33. MASS ASSIGNMENT

Procure objetos em que o cliente possa enviar campos inesperados.

Por exemplo, avalie conceitualmente se um atacante poderia tentar alterar:

* `role`;
* `admin`;
* `ownerId`;
* `userId`;
* `status`;
* `verified`;
* `permissions`;
* `price`;
* `discount`;
* campos internos;
* timestamps;
* IDs.

A solução deve utilizar allowlists explícitas de campos mutáveis.

---

# 34. IDOR / ENUMERAÇÃO

Teste IDs:

* sequenciais;
* UUID;
* slugs;
* códigos;
* nomes;
* parâmetros.

Verifique se alterar identificadores permite acesso a objetos que pertencem a outra pessoa.

# 35. INFORMATION DISCLOSURE

* respostas;
* erros;

* mensagens;
* APIs;
* páginas 404;

* nomes internos.

Não exponha:

* SQL;
* paths internos;
* secrets;
* tokens;
* stack traces;
* informações de infraestrutura;
* dados de outros usuários.

# 36. ERROR HANDLING

Force erros de maneira segura.

Verifique:

* inputs inválidos;
* IDs inexistentes;
* tipos errados;
* JSON inválido;
* autenticação ausente;
* autorização ausente;
* exceções inesperadas.

A aplicação deve:

* falhar de maneira segura;
* retornar códigos HTTP apropriados;
* não vazar informações internas;
* registrar o necessário internamente;
* não revelar secrets.

# 37. CRIPTOGRAFIA

* hashing;
* tokens;
* secrets;
* cookies;
* dados sensíveis;
* geração aleatória;
* IDs temporários;
* URLs assinadas.

Procure:

* MD5;
* SHA-1 para segurança;
* hashes inadequados de passwords;
* randomização fraca;
* secrets hardcoded;
* chaves previsíveis;
* criptografia customizada.

* X-Content-Type-Options;
* Referrer-Policy;
* Permissions-Policy;

* cache controls;
* cookies.

* endpoints administrativos;

* contornar limites;
* automatizá-la.

# 59. PENTEST BASEADO EM PERSONAS

Usuário tentando manipular APIs diretamente.

### Cenário E

Atacante tentando extrair secrets.

Atacante tentando abusar da lógica de negócio.

Atacante com conhecimento completo do código-fonte.

# 60. NÃO CONFIE NO FRONTEND

Para todas as regras importantes:

Ignore temporariamente a interface.

Tente raciocinar como se tivesse somente:

* HTTP client;
* browser DevTools;
* API client;
* conhecimento do código.

Tudo que for importante deve ser validado no servidor.

---

# 61. FASE DE CORREÇÃO

Após encontrar uma vulnerabilidade:

NÃO apenas documente.

Corrija.

A correção deve:

1. eliminar a causa raiz;
2. não apenas bloquear o payload específico;
3. preservar o funcionamento legítimo;
4. não criar vulnerabilidade secundária;
5. possuir teste de regressão;
6. possuir validação server-side;
7. ser aplicada em todas as rotas equivalentes.

Exemplo:

Se encontrar um IDOR em `/api/x`, procure imediatamente endpoints equivalentes que possam sofrer do mesmo problema.

---

# 62. VARIANT ANALYSIS

Depois de corrigir cada vulnerabilidade:

Pergunte:

> "Onde mais esse mesmo padrão pode existir?"

Procure:

* endpoints semelhantes;
* funções semelhantes;
* queries semelhantes;
* componentes semelhantes;
* outras tabelas;
* outras roles;
* outras APIs.

Corrija a classe inteira do problema.

---

# 63. TESTE DE REGRESSÃO

Depois das correções:

Execute novamente todos os testes relevantes.

Confirme:

* ataque original bloqueado;
* variantes bloqueadas;
* usuário legítimo continua funcionando;
* administrador continua funcionando;
* integração continua funcionando;
* banco continua consistente.

# 66. DYNAMIC ANALYSIS

* cookies;

* APIs;
* erros;
* comportamento inesperado.

NÃO realize flooding.

NÃO exfiltre dados reais.

Utilize dados de teste.

* evite carga;
* evite alteração permanente;
* não utilize dados reais;
* não exfiltre dados;
* não tente causar indisponibilidade.

# 72. CRITÉRIO DE CONCLUSÃO

NÃO encerre a auditoria simplesmente porque:

* os testes passam;
* o build funciona;
* não há erros no console;
* `npm audit` está limpo;
* o frontend parece seguro;
* não foram encontradas vulnerabilidades óbvias.

A auditoria só deve ser considerada concluída depois de:

1. mapear a superfície de ataque;
2. revisar o código;
3. revisar arquitetura;
4. revisar banco;
5. revisar autenticação;
6. revisar autorização;
7. revisar APIs;
8. revisar infraestrutura;
9. revisar dependências;
10. testar lógica de negócio;
11. procurar secrets;
12. procurar vulnerabilidades;
13. corrigir vulnerabilidades;
14. procurar variantes;
15. criar regressões quando apropriado;
16. executar novamente a auditoria;
17. confirmar que as correções realmente funcionam.

---

# 73. REGRA DE "ASSUMIR COMPROMETIMENTO"

Ao encontrar um segredo exposto, considere que ele pode ter sido comprometido.

Ao encontrar uma vulnerabilidade de autorização, considere que dados podem ter sido acessíveis.

Ao encontrar uma vulnerabilidade de sessão, considere que sessões podem ter sido comprometidas.

Ao encontrar uma vulnerabilidade de API, considere que ela pode ser explorada diretamente sem frontend.

Não minimize riscos apenas porque não encontrou evidência de exploração.

---

# 74. NÃO CORRIJA COM GAMBARRAS

Não utilize:

* verificações duplicadas espalhadas;
* blacklists frágeis;
* validações apenas frontend;
* regex inadequadas;
* `if` improvisados;
* ocultação de endpoints;
* obscuridade como segurança;
* hardcoded secrets;
* permissões excessivas.

Prefira:

* arquitetura segura;
* princípios de least privilege;
* deny by default;
* allowlists;
* validação server-side;
* schemas;
* constraints;
* RLS;
* transações;
* políticas explícitas;
* funções pequenas;
* abstrações reutilizáveis;
* testes automatizados.

# 75. PRINCÍPIO DE DEFESA EM PROFUNDIDADE

Frontend
↓
Server validation
↓
Authentication
↓
Authorization
↓
Business rules
↓
Database constraints / RLS
↓
Infrastructure controls
↓
Monitoring

Uma falha em uma camada não deve resultar automaticamente em comprometimento completo.

# 77. NÃO INTRODUZA REGRESSÕES

Após cada conjunto de alterações:

* lint;
* typecheck;
* build;
* testes;
* testes de segurança;
* testes específicos da funcionalidade.

* investigue;
* corrija;
* não simplesmente desabilite o teste.

# 78. SEGURANÇA SEM QUEBRAR FUNCIONALIDADE

O objetivo não é tornar o sistema inutilizável.

Equilibre:

* segurança;
* performance;
* UX;
* disponibilidade;
* compatibilidade;
* manutenção.

Se uma correção puder quebrar comportamento legítimo, analise antes de aplicar.

---

# 79. SEGURANÇA DE PERFORMANCE

Verifique se as proteções introduzidas não geram:

* queries desnecessárias;
* N+1;
* operações caras;
* bloqueios;
* aumento excessivo de latência;
* gargalos.

Uma proteção de segurança que permite fácil DoS por ser excessivamente custosa também é problemática.

---

# 80. AUDITORIA FINAL ADVERSARIAL

Depois de todas as correções, faça uma segunda auditoria do zero.

IMPORTANTE:

Finja que você NÃO sabe quais vulnerabilidades encontrou anteriormente.

Recomece como um novo pentester.

Pergunte:

> "Se eu fosse um atacante vendo esta aplicação pela primeira vez, onde tentaria entrar?"

Faça novamente:

* reconnaissance;
* attack surface mapping;
* authentication testing;
* authorization testing;
* API testing;
* input validation;
* business logic;
* session testing;
* configuration review;
* dependency review;
* secrets review.

Somente depois compare com a primeira auditoria.

---

# 81. TESTE DE CADEIAS DE ATAQUE

Não avalie vulnerabilidades apenas isoladamente.

Procure combinações como:

* information disclosure → account takeover;
* XSS → session compromise;
* IDOR → data exposure;
* weak authorization → privilege escalation;
* SSRF → internal access;
* exposed secret → database access;
* API abuse → resource exhaustion;
* business logic flaw → financial impact.

Uma vulnerabilidade Medium isolada pode se tornar Critical quando combinada com outra.

# 83. CRITÉRIO DE QUALIDADE

Quero uma análise equivalente ao trabalho de um profissional de AppSec realizando uma revisão profunda de uma aplicação SaaS real.

Não quero uma resposta genérica.

Não quero somente recomendações.

Não quero apenas uma checklist.

Quero:

**descoberta → exploração controlada → evidência → causa raiz → correção → teste → variant analysis → regressão → reauditoria.**

# 84. REGRAS DE SEGURANÇA DURANTE O PENTEST

Todos os testes devem ser autorizados e realizados exclusivamente contra:

* o código deste projeto;
* ambientes pertencentes ao projeto;
* infraestrutura pertencente ao projeto;
* dados de teste.

NÃO:

* destrua dados;
* provoque indisponibilidade;
* faça flooding;
* exfiltre dados reais;
* publique secrets;
* ataque terceiros;
* ataque serviços externos que não façam parte do escopo;
* utilize dados reais de usuários para testes.

Quando uma exploração destrutiva seria necessária para comprovar uma vulnerabilidade, não execute a parte destrutiva. Demonstre o risco de forma controlada.

# 85. INSTRUÇÃO FINAL — NÃO PARE NA PRIMEIRA VULNERABILIDADE

Depois de encontrar uma vulnerabilidade, NÃO considere a categoria encerrada.

Pergunte:

> "Qual é a causa sistêmica?"

Depois:

> "Onde mais essa causa pode existir?"

Depois:

> "Qual variante um atacante tentaria?"

Depois:

> "A correção pode ser contornada?"

Depois:

> "Existe outra camada que deveria impedir isso?"

Repita até não encontrar novas variantes relevantes.

# 86. PRIMEIRA AÇÃO

Comece agora.

Primeiro:

1. faça o inventário completo do repositório;
2. identifique a arquitetura;
3. identifique todas as superfícies de ataque;
4. faça a análise de secrets, especialmente `.env` e histórico Git;
5. faça o threat model;
6. mapeie autenticação/autorização;
7. mapeie APIs;
8. mapeie banco/Supabase/RLS/Prisma;
9. execute a revisão de segurança;
10. corrija os problemas encontrados;
11. execute os testes;
12. faça variant analysis;
13. faça uma segunda auditoria independente;
14. gere o relatório final.

NÃO entregue apenas recomendações.

**Implemente as correções necessárias no código quando for seguro fazê-lo.**

Ao final, só classifique uma vulnerabilidade como "corrigida" quando houver evidência de que:

* a causa raiz foi corrigida;
* a exploração original deixou de funcionar;
* variantes relevantes também foram bloqueadas;
* os testes de regressão passam;
* a funcionalidade legítima continua funcionando.

Comece pela análise do repositório e pelo inventário da superfície de ataque.
